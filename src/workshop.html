CI/CD Workshop Manual

Build a personal website and deploy it automatically with GitHub Actions.

🎯 Overview

In this workshop, you will:

  • Build a simple personal website (HTML, CSS, JavaScript)
  • Push it to GitHub
  • Write a CI/CD pipeline using GitHub Actions
  • Watch it automatically test, build, and deploy to a live URL

By the end, you'll have:

  • A live website at https://YOUR-USERNAME.github.io/website-demo/
  • A working CI/CD pipeline triggered on every push
  • Real experience with the tools professional developers use
💡 What is CI/CD? CI (Continuous Integration) = Every time you push code, tests run automatically.
CD (Continuous Deployment) = If tests pass, your code is deployed automatically.

⚙️ Part 4: Create the CI/CD Pipeline

1Enable GitHub Pages (Critical!)

🚨 Do this BEFORE running the workflow If you skip this, your deploy job will fail with "Get Pages site failed. Not Found".
  1. Go to your repository on GitHub
  2. Click Settings (top menu)
  3. Left sidebar → Pages
  4. Under Build and deployment → Source: choose "GitHub Actions"
  5. No branch selection needed — just pick "GitHub Actions" from the dropdown
💡 Why this step? GitHub Pages has two modes: "Deploy from a branch" (legacy) and "GitHub Actions" (modern). Our workflow uses the modern mode. Without selecting it, GitHub doesn't know to expect a workflow deployment.

2Create the Workflow File

Terminal
mkdir -p .github/workflows
nano .github/workflows/deploy.yml
.github/workflows/deploy.yml
name: 🚀 Build and Deploy Website

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]
  workflow_dispatch:

permissions:
  contents: read
  pages: write
  id-token: write

concurrency:
  group: "pages"
  cancel-in-progress: false

jobs:
  # ══════════════════════════════════════════════
  # JOB 1: TEST — Validate the website
  # ══════════════════════════════════════════════
  test:
    name: 🧪 Test
    runs-on: ubuntu-latest
    steps:
      - name: 📥 Checkout code
        uses: actions/checkout@v4

      - name: ✅ Verify required files exist
        run: |
          echo "Checking for required files..."
          test -f src/index.html || (echo "❌ src/index.html missing" && exit 1)
          test -f src/style.css  || (echo "❌ src/style.css missing" && exit 1)
          test -f src/script.js  || (echo "❌ src/script.js missing" && exit 1)
          echo "✅ All required files present!"

      - name: 🔍 Validate HTML structure
        run: |
          echo "Validating HTML..."
          grep -q "" src/index.html || (echo "❌ Missing DOCTYPE" && exit 1)
          grep -q " tag" && exit 1)
          grep -q "" src/index.html    || (echo "❌ Missing " && exit 1)
          grep -q "" src/index.html    || (echo "❌ Missing " && exit 1)
          echo "✅ HTML structure is valid!"

  # ══════════════════════════════════════════════
  # JOB 2: BUILD — Package the site
  # ══════════════════════════════════════════════
  build:
    name: 🏗️ Build
    runs-on: ubuntu-latest
    needs: test
    steps:
      - name: 📥 Checkout code
        uses: actions/checkout@v4

      - name: 📁 Create build directory
        run: |
          mkdir -p dist
          cp -r src/* dist/
          echo "Build complete!"

      - name: 📝 Add build info file
        run: |
          echo "Build Date: $(date -u)" > dist/build-info.txt
          echo "Commit SHA: ${{ github.sha }}" >> dist/build-info.txt
          echo "Branch: ${{ github.ref_name }}" >> dist/build-info.txt
          echo "Triggered by: ${{ github.actor }}" >> dist/build-info.txt

      - name: 📤 Upload build artifact
        uses: actions/upload-artifact@v4
        with:
          name: website-build
          path: dist/
          retention-days: 7

  # ══════════════════════════════════════════════
  # JOB 3: DEPLOY — Publish to GitHub Pages
  # ══════════════════════════════════════════════
  deploy:
    name: 🚀 Deploy
    runs-on: ubuntu-latest
    needs: build
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    environment:
      name: github-pages
      url: ${{ steps.deployment.outputs.page_url }}
    steps:
      - name: 📥 Checkout code
        uses: actions/checkout@v4

      - name: 📁 Prepare site files
        run: |
          mkdir -p _site
          cp -r src/* _site/
          echo "Site ready for deployment"

      - name: 🔧 Configure GitHub Pages
      uses: actions/configure-pages@v5

      - name: 📤 Upload Pages artifact
        uses: actions/upload-pages-artifact@v3
        with:
          path: _site

      - name: 🌐 Deploy to GitHub Pages
        id: deployment
        uses: actions/deploy-pages@v4

    This is the most important file in your CI/CD pipeline. Every line has a purpose.
    Let's break it down piece by piece.
  


  
  
📌 Section 1: Workflow Name

  
  

    
Line 1


name: 🚀 Build and Deploy Website

  


  

    
PartMeaning

    
name:The YAML key for the workflow's display name

    
🚀 Build and Deploy WebsiteWhat appears in the Actions tab on GitHub

  


  

    💡 Where you see it
    Go to your repo → Actions tab → left sidebar shows this name.
    Optional, but always include it — otherwise GitHub shows the filename instead.
  


  
  
📌 Section 2: Triggers — When Does It Run?

  
  

    
Lines 3-9


# When does this run?
on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]
  workflow_dispatch:   # Allows manual trigger from GitHub UI

  


  
This is the most important section — it defines when the workflow runs.


  

    
LineCodeMeaning

    
3# When does this run?A comment — YAML ignores everything after #

    
4on:Start of trigger list

    
5push:Trigger when code is pushed

    
6branches: [ main ]Only for the main branch

    
7pull_request:Trigger on PRs targeting...

    
8branches: [ main ]...the main branch

    
9workflow_dispatch:Adds a manual "Run workflow" button

  


  

    💡 Push vs Pull Request
    push = "someone pushed code"

    pull_request = "someone opened/updated a PR"

    Both can trigger on the same commit — they're separate events.
  


  
  
📌 Section 3: Permissions

  
  

    
Lines 11-15


# Permissions the workflow needs
permissions:
  contents: read
  pages: write
  id-token: write

  


  
By default, GitHub Actions workflows get a read-only token for security. If your workflow needs to write anything, you must explicitly grant it.


  

    
PermissionWhy It's Needed

    
contents: readRead repo files (for actions/checkout)

    
pages: writePublish to GitHub Pages

    
id-token: writeAuthenticate via OIDC (GitHub's digital ID card)

  


  

    🚨 Without this block
    Your deploy job fails with "Resource not accessible by integration".
    This is the #1 cause of deploy failures.
  


  
  
📌 Section 4: Concurrency — Preventing Collisions

  
  

    
Lines 17-20


# Prevent concurrent deploys from clobbering each other
concurrency:
  group: "pages"
  cancel-in-progress: false

  


  
If you push 3 times in 30 seconds, 3 workflows start. Concurrency control prevents them from deploying simultaneously.


  

    
LineCodeMeaning

    
18concurrency:Start of concurrency settings

    
19group: "pages"Name of the queue — all workflows with this name share it

    
20cancel-in-progress: falseQueue new runs instead of canceling old ones

  


  

    ⚠️ Why false here?
    Deploys are irreversible. Canceling mid-deploy can leave a half-deployed site.
    For test-only workflows, use true — no harm in canceling tests.
  


  
  
📌 Section 5: The Three Jobs

  
  
Our workflow has three jobs, running in sequence:


  

    
JobPurposeRuns If

    
testValidate files and HTMLAlways (on trigger)

    
buildPackage for deployTest passed

    
deployPublish to GitHub PagesBuild passed AND on main branch

  


  

    💡 Key concept
    Each job runs on its own fresh virtual machine. Files don't carry over unless explicitly uploaded/downloaded.

Lines 23-50


test:
  name: 🧪 Test
  runs-on: ubuntu-latest
  steps:
    - name: 📥 Checkout code
      uses: actions/checkout@v4

    - name: ✅ Verify required files exist
      run: |

Line-by-Line Explanation

  
  

    
LineCodeMeaning

    
23test:Job ID — unique name for referencing this job

    
24name: 🧪 TestDisplay name in the UI

    
25runs-on: ubuntu-latestOS for the runner VM (Linux, cheapest, fastest)

    
26steps:List of tasks in this job

    
27-28- name: ... uses: actions/checkout@v4First step — clones your repo onto the VM

    
30-36- name: ... run: |Second step — check files exist

  


  
Understanding the shell logic

  
  

    
Breaking down one line


test -f src/index.html || (echo "❌ missing" && exit 1)

  


  
This uses bash's logical operators:

  
    
    
  • test -f src/index.html → returns 0 if the file exists, 1 if not
    • 
    
  • || → "OR" — run next command only if first one failed
    • 
    
  • (echo "❌ missing" && exit 1) → print error AND exit with failure code
    • 
  


  
Result: If the file exists → skip the error, continue. If missing → print error and fail the job.


  

    💡 The | pipe character
    It tells YAML: "Everything indented below is one multi-line string."
    Without it, you'd need to write commands on one line.
  


  
Validate HTML Step


  

    
HTML validation


- name: 🔍 Validate HTML structure
  run: |
    grep -q "" src/index.html || (echo "❌ Missing DOCTYPE" && exit 1)
    grep -q " tag" && exit 1)
    grep -q "" src/index.html    || (echo "❌ Missing " && exit 1)
    grep -q "" src/index.html    || (echo "❌ Missing " && exit 1)

  


  

    
FlagMeaning

    
grepSearch for a pattern in a file

    
-qQuiet mode — no output, just exit code (0 if found, 1 if not)

  


  
Why this matters: Catches corrupted or truncated HTML files before they deploy.

OperatorMeaning

    
>Overwrite the file (creates if doesn't exist)

    
>>Append to the file (adds to end)

The Safety Guard — Line 84

  
  

    
Line 84


if: github.ref == 'refs/heads/main' && github.event_name == 'push'

  


  
Breaking it down:

  
    
    
  • github.ref == 'refs/heads/main' → Is this a push to main?
    • 
    
  • && → AND
    • 
    
  • github.event_name == 'push' → Is this event a push?
    • 
  


  
Why both conditions: PRs would also match main in some cases — we don't want to deploy unmerged code.


  

    🚨 Rule of thumb
    Deploy jobs always need if: guards. Never let them run on PRs.

⚠️ Common Mistakes


  

    
MistakeWhy It FailsFix

No if: guard on deployDeploys on PRsAdd if: github.ref == 'refs/heads/main'

    
Forgetting needs:Jobs run in parallelAdd needs: <job-id>

    
Using @main for actionsActions can break unexpectedlyPin to @v4 major version

    
Missing checkoutNo files on runnerAdd actions/checkout@v4
